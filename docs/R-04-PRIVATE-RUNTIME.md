# R-04 report drafts in the opt-in private runtime

The private R-03 web runtime can mount the shared accepted-candidate report workflow only when it is explicitly started with `--connected-bff`, its issuer/origin/BFF database configuration, and `--report-drafts-db /absolute/private/path/reports.sqlite`. The separate `report_drafts_encryption_key` must be supplied through the owner-only secrets directory. Without that flag, the runtime does not construct the encrypted report store, cold-search report source, HH-response report source, or report routes. The default service unit does not load the report key or pass the flag.

For an HH response source, the runtime reads the exact negotiation and current `/resumes/{id}` record using the profile-bound HH credential. It maps the current resume with the current private vacancy plan, then compares that exact mapped input to ATS assessments from accepted scheduled/manual snapshots. The stored assessment input revision includes the snapshot's source revision, vacancy criteria revision and complete mapped candidate projection. The assessment reader accepts only a matching current criteria revision and active/starred review overlay. Unknown/unaccepted snapshots, changed resume facts, archived candidates, and foreign profile/vacancy bindings cannot supply a report.

Only the selected client allowlist is stored in the report draft. The raw HH resume is never returned by the report source port or persisted to the report database. The reader has no messages endpoint, creates no new ATS evaluation, and does not send, publish or share a report. A current CP Connected App session and the report read/create/review scopes are required by the HTTP/BFF handlers.

CI exercises the composed private runtime with invented CP and HH transports, accepted synthetic SQLite snapshot/assessment/occurrence data, a real encrypted draft store, OAuth step-up, HTTP create/preview, process restart, source staleness, owner-only file modes, and a zero-message-call assertion. This proves the opt-in software path. The default host service remains unchanged; an owner-reviewed private profile/vacancy mapping, product-approved client field policy, and separate live canary are still required before enabling it on the RU host.
