# R-03 real HH result contract and private candidate state

This slice adds `hh-result-v1` in `contracts/v1-real-hh-result.schema.json` and a separate `SqliteRealHhCandidateState`. It accepts the pure mapped projection from `src/hh-resume-mapping.js`, never the full `/resumes` response. Its allowlist rejects extra candidate or top-level fields, including a raw provider payload. The result has profile, vacancy, job, criteria and source revisions, search time, source (manual/scheduled), total collected and the complete post-experience candidate pool. The pre-score is a prioritization hint. ATS score and arbitrary knockout remain pending; this version explicitly requires null ATS fields.

One transaction writes the accumulating candidate pool, per-profile/per-vacancy seen IDs, and a dated result snapshot with immutable ordered member projections. Candidate identity is profile-wide; seen state is vacancy-specific. A repeated job with identical input returns the original snapshot; a conflicting replay fails. Page reads use a deterministic pre-score/ID order and a snapshot-bound cursor. Tests exercise 257 invented candidates, restart, two SQLite connections, rollback before commit, duplicate/invalid IDs and profile isolation. The existing synthetic job and candidate-state models and their routes are unchanged.

`latest_projection` is one profile-wide candidate copy and may be replaced when the same resume appears in another vacancy. Immutable snapshot members preserve each search's vacancy-specific projection, but this slice does not yet model an accumulated per-vacancy candidate feed, reviews or comments. Add explicit candidate-vacancy membership and assessment revisions before serving a live morning page from these tables.

The database must be placed in an owner-only `0700` directory and is chmod `0600` on open. SQLite WAL files remain inside that directory. The service account must be the sole filesystem owner; backups must preserve the same access boundary. These projections contain names, resume URLs, salary and work history, so the DB, WAL, backups and any future exports are private. A retention period, deletion workflow, encryption policy, consent basis, backup expiry and candidate access audit still require an owner decision before live data. This adapter does not implement those policies and is not configured for production.

Integration still needs a trusted profile/vacancy context and credential owner, multi-query HH collection, final ATS/LLM assessment with revisioned background rescore, a real job contract with more than the synthetic 200-result cap, authenticated page/API projection, and worker/route cutover. No live HH call, LLM call, route, schedule or production write is connected in this slice.
