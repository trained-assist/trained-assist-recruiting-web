# R-03 durable candidate state foundation

`SqliteCandidateStateStore` is an **opt-in** implementation of the `createCandidateState` store port. Pass it to `createRecruitingServer({ candidateStateStore })`. The default remains synthetic in-memory state. It may use the **same private SQLite file** as `SqliteCandidateSearchJobs` and `SqliteColdSearchScheduleRepository`; each opens its own connection. The directory must be owner-only (`0700`), including the WAL/SHM sidecars, and the database file is set to `0600`.

Each profile has one versioned JSON row. `BEGIN IMMEDIATE` reloads that row, runs the domain mutation and commits it as one SQLite transaction. A completed search therefore commits the full candidate pool, per-vacancy seen ledger and dated snapshot together. An exception at any stage rolls all three back. Two connections and a separate process observe serialized updates. Replaying the same completed job ID returns its original snapshot; a different candidate set or vacancy for the same job ID conflicts. Reads stay bound to the trusted profile and owned vacancy through `createCandidateState`.

## Job → candidate-state reconciliation boundary

The job adapter commits its completed provider result before `recordSearch` commits the candidate state. They cannot form one transaction through the current independent adapter APIs, even when they share the SQLite file. A crash or state write failure between these commits leaves a completed job with no candidate snapshot. It must **not** be presented as a fresh result. Manual `/api/hh/proactive/search` returns typed `503 search_outcome_unknown` on a state exception. A retry with the same idempotency key reads the completed job and materializes the missing snapshot without another provider call. A scheduled occurrence becomes `outcome_unknown` and stays blocked; an operator must reconcile the completed job and snapshot for its trusted `(profileId, vacancyId, occurrenceId)` before marking the occurrence resolved. Never dispatch a second provider search merely because the snapshot is missing.

The reconciliation check is: locate a completed job by its deterministic `schedule:<occurrenceId>` key or manual key; compare its profile, vacancy, criteria and source revision with the claimed occurrence/request; inspect whether `snapshotsByVacancy[vacancyId]` contains that `jobId`; if absent, materialize its committed result through `recordSearch` using the job's persisted `completedAt` and original source; if present, verify the same candidate references. The SQLite job adapter stamps `completedAt` when it commits the final page so a retry after restart does not fabricate morning freshness. [The offline reconciler](R-03-OFFLINE-RECONCILIATION.md) now handles completed scheduled jobs and issues an atomic receipt. Production operator identity/CLI and audit sink are still missing. The current in-memory manual operation map does not survive restart, but the durable job key and idempotent snapshot permit a safe same-key retry.

This adapter stores one growing JSON document per profile. It needs retention, backup/restore, schema migration, privacy controls, and a scalable query/index design before real candidate data. It does not enable HH credentials, background rescoring, legacy import, public routing or GCP VM shutdown. The tests use synthetic IDs and data only.
