# R-03 profile-bound HH credential broker

`createPrivateHhCredentialBroker` supplies `loadCredential` and `refreshCredential` to the existing HH transport. A trusted server-side binding maps a profile ID to an owner-only token directory; neither HTTP nor MCP input selects the path. The reader accepts only the AES-256-GCM v2 envelope, requires the encryption key, and rejects plaintext, non-canonical envelopes, symlinks, group/world-readable files and malformed credentials without returning source content in errors. Legacy plaintext files must be encrypted during private-data restore before the worker can use them.

On a 401/403, the transport calls refresh once. The broker takes a per-file cross-process lock, re-reads the credential after locking, and avoids a second OAuth POST if another process already rotated it. A successful OAuth response replaces the token atomically with an encrypted v2 file (`0600`) and syncs the file and directory. A failed OAuth request leaves the old token and releases the lock. An orphaned lock after process death is **not** removed automatically; an operator must investigate before clearing it, because an in-flight refresh may have had an uncertain outcome.

Tests use invented credentials and mock HH/OAuth responses. No real token, OAuth client secret, target profile mapping or HH request was used. The broker's encryption gate covers the replacement worker's file read path; the separate HH Skill credential store is not imported by this worker. A real target acceptance run still needs private data restore into v2 files, secret delivery, operator recovery for orphaned locks, authorized HH canary, scorer, timer and route cutover.
