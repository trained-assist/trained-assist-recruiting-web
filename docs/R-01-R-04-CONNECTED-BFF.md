# R-01/R-04 Connected App BFF boundary

This opt-in slice consumes the Control Plane [Authorization Code + PKCE S256 profile](https://github.com/trained-assist/trained-assist-control-plane/pull/70) for Recruiting. It is stacked on integration PR #73. The default server does not construct or mount it. No live issuer, credential, public route or RU service was changed.

`createRecruitingConnectedAppBff` requires an exact HTTPS issuer and public origin, callback URI, server-side `exchangeCode` and `introspectToken` ports, and a store with atomic `takePending`. `createControlPlaneConnectedAppClient` maps those ports to the first-party CP endpoints with a Recruiting-only service credential. The memory store exported here is a synthetic test fixture; production requires a durable session/transaction store shared by every web process.

1. The BFF generates a transaction-specific state and PKCE verifier, stores both server side, and sends the browser to CP with `response_type=code`, `client_id=recruiting-web`, exact callback, requested scopes and S256 challenge. A short `__Host-recruiting-oauth-pending` cookie identifies the pending transaction; it is HttpOnly, Secure and SameSite=Lax for the top-level callback navigation.
2. The callback consumes the pending transaction once, compares exact state and issuer, exchanges the code with its service credential and verifier, then introspects the resulting opaque token. Only after a valid Recruiting audience, issuer, subject, selected profile, session, lifetime and allowed scopes does the BFF store the token server side. The browser receives a separate random `__Host-recruiting-app-session` handle in an HttpOnly, Secure, SameSite=Strict cookie. Code and token are absent from the final redirect.
3. Every R-01/R-04 read using this opt-in BFF resolves the cookie through a fresh CP introspection and checks the same subject/profile/session as at callback. Inactive token, changed profile, wrong audience/issuer or wrong operation scope fails closed. The BFF session endpoint exposes only profile, scopes and a CSRF token. Unsafe methods require the exact public Origin and CSRF header. Logout deletes the local session and cookie; platform-wide token revocation still belongs to CP.

To use this outside synthetic tests, implement a durable atomic store, register the exact CP BFF client/redirect and private service credential, connect a live CP user/profile authority resolver and real issuer, mount only behind the intended HTTPS origin, prove same-origin CSRF on every future mutation, and test logout/profile switch/revocation with real sessions. The existing R-03 signed page cookie remains separate. The legacy agent web JWT and browser-supplied profile ID are not accepted.

This is a closed first-party BFF integration, following [RFC 10017 §6.1](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.1) and [RFC 9700 §2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1). It does not claim a deployed OAuth/OIDC integration or production-ready login.
