# R-01/R-04 Connected App BFF boundary

This opt-in slice consumes the Control Plane [Authorization Code + PKCE S256 profile](https://github.com/trained-assist/trained-assist-control-plane/pull/70) for Recruiting. It is stacked on integration PR #73. The default server does not construct or mount it. No live issuer, credential, public route or RU service was changed.

`createRecruitingConnectedAppBff` requires an exact HTTPS issuer and public origin, an explicit allowed issuer-origin list, callback URI, server-side `exchangeCode` and `introspectToken` ports, and a store with atomic `takePending`. `createControlPlaneConnectedAppClient` maps those ports to two fixed first-party CP endpoints with a Recruiting-only service credential and the same outbound allowlist; it does not follow outbound redirects. The memory store exported here is a synthetic test fixture; production requires a durable session/transaction store shared by every web process.

1. The BFF generates a transaction-specific state and PKCE verifier, stores both server side, and sends the browser to CP with `response_type=code`, `client_id=recruiting-web`, exact callback, requested scopes and S256 challenge. A short `__Host-recruiting-oauth-pending` cookie identifies the pending transaction; it is HttpOnly, Secure and SameSite=Lax for the top-level callback navigation.
2. The callback consumes the pending transaction once, compares exact state and issuer, exchanges the code with its service credential and verifier, then introspects the resulting opaque token. Only after a valid Recruiting audience, issuer, subject, selected profile, session, lifetime and allowed scopes does the BFF store the token server side. The browser receives a separate fresh random `__Host-recruiting-app-session` handle in an HttpOnly, Secure, SameSite=Strict cookie; an earlier handle is invalidated to prevent fixation. Code and token are absent from the final redirect. The return destination is the server-owned `/hh/proactive` landing or that same path with one validated `vacancy_id`, on the exact public origin. Absolute or arbitrary browser-provided redirects are rejected.
3. Every R-01/R-04 read using this opt-in BFF resolves the cookie through a **fresh no-cache** CP introspection and checks the same subject/profile/session as at callback. An explicit inactive token fails closed with 401. Network failure, malformed introspection or a non-success CP response yields typed `connected_app_introspection_unavailable` and HTTP 503 for protected reads, without deleting local membership. The BFF session endpoint exposes only profile, scopes and a CSRF token. Unsafe methods require the exact public Origin and CSRF header. Logout deletes the local session and cookie even during CP outage; platform-wide token revocation still belongs to CP. No access token or authorization code is written to the BFF's logs.

The private R-03 web CLI now has a separate `--connected-bff` mode. It composes `SqliteConnectedAppBffStore`, the CP client and this BFF behind the real `/hh/proactive` handlers. The store uses SQLite `DELETE ... RETURNING` to consume each pending transaction once across processes and restarts. Pending PKCE material, browser session, CSRF value and CP access token are AES-256-GCM sealed before SQLite or WAL writes; the key comes from a service credential. Both stores prune expired records on writes, and session reads reject expired records. The service must run as its dedicated owner with a private `0700` state directory, a private `0600` database, persistent `bff_encryption_key` and the exact registered issuer, client, callback and service key. A lost encryption key invalidates existing browser sessions and pending handoffs; it must never be committed or printed. The separate disabled-by-default [systemd unit](../infra/systemd/trained-recruiting-hh-web-bff.service) has no `legacy_page_secret`, and the [ingress fragment](../infra/nginx/recruiting-connected-bff.locations.conf) disables access logs for the callback URL. The existing signed-link unit does not enable BFF mode. Both modes cannot run in the same process.

An unauthenticated visit to `/hh/proactive` redirects to the fixed BFF start route. A deep link can carry one validated vacancy ID through the one-use pending transaction. A CP chooser login without a vacancy returns to `/hh/proactive`; when a profile owns several configured vacancies, the server shows a picker containing only that profile's configured vacancy IDs. An unbound profile gets 404. The picker does not choose the first vacancy or query another profile's feed.

Production activation still requires the CP platform login/profile resolver, registered exact callback and private service credential, a live issuer, proxy wiring, and real-session acceptance including logout, profile switch and revocation. A browser profile switch only invalidates browser grants; it must not retarget an already accepted task or automatically revoke a schedule grant. Those are separate caller classes with their own owner/revocation rules. The legacy agent web JWT and browser-supplied profile ID are not accepted.

This is a closed first-party BFF integration, following [RFC 10017 §6.1](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.1) and [RFC 9700 §2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1). It does not claim a deployed OAuth/OIDC integration or production-ready login.
