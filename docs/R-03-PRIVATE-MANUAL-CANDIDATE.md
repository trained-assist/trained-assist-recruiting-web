# R-03 manual HH candidate

A recruiter pastes a bare HH resume ID or an `https://hh.ru/resume/...` link into the morning page for a specific vacancy. `POST /api/hh/proactive/add-manual` takes `vacancy_id` and `resume_url_or_id` under the trusted profile session and same-origin POST check. It rejects foreign hosts, unowned vacancies and extra legacy fields. There is no active-vacancy or wildcard fallback.

The private service obtains the profile's HH credential, fetches exactly `/resumes/{id}` with a 20-second request timeout, refreshes an expired credential at most once, requires the returned ID to match, and maps only the bounded candidate projection. A recruiter-selected resume bypasses the search's minimum-experience exclusion; this matches the old manual-add behavior. The raw HH response and token are not persisted or returned. SQLite inserts the candidate into a profile/vacancy `real_hh_manual_candidate` table atomically. Repeated adds return `added: false` without another HH call. The accepted feed includes the manual candidate independently of search receipts; it does not create a fake search snapshot or fresh schedule result. A later accepted search can supersede the displayed projection by timestamp. Review status and comments remain vacancy-scoped. Manual additions currently have pending ATS assessment; the background scorer still works only on accepted search snapshots.

Synthetic tests cover explicit scope, malformed links, duplicate behavior, one token refresh, mismatched HH ID, transaction rollback, HTTP and browser request shape. No live HH call, route switch or public credential is part of this slice.
