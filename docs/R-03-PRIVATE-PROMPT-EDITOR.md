# R-03 private query editor

The private morning page now reads and edits the vacancy's HH search queries through `GET/POST /api/hh/proactive/prompt`. The browser uses its target-profile cookie. The new command carries `vacancy_id`, `queries`, `expected_revision` and `expected_override_revision`; the profile remains server supplied. A stale tab receives 409 and reloads the current list before another save. Queries are trimmed, unique, nonempty, at most 15 lines and at most 500 characters each. An empty list requests reset. Invalid input or a different profile/vacancy cannot write.

`SqlitePrivateQueryOverrides` stores a revisioned manual query set or an explicit reset tombstone in the target SQLite database. The shared private base search plan reads it before dispatch, so both scheduled and manual HH searches use the edited queries. A manual set remains pinned through ATS feedback, matching the old editor intent. A reset ignores even a manually pinned file in the frozen source and generates into a target-side cache keyed by the reset revision. The source `queries-<vacancy>.json` is never rewritten. A reset returns 202 because regeneration can take place on the next read; if the generator is unavailable, the reset persists and search fails closed instead of using the stale source.

The old `/prompt` response also contained an explanation of the scoring prompt. This slice does not expose one; the existing ATS editor and query generator retain separate responsibilities. Existing open GCP tabs still send legacy JSON `username`/`token`, so they are incompatible after a route switch. Public nginx routing and live credentials/data remain unchanged. Tests use invented profiles, vacancies and queries, plus a browser request fixture. The real host needs source restore, credential checks, HH/LLM canaries and route acceptance before cutover.
