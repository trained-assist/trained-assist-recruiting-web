# R-03 existing open-tab migration

The old proactive page sends JSON `username` and 16-hex page `token` on every POST. It does not hold the new `__Host-r03-proactive` cookie. Its JavaScript displays the API's `error` string in an alert, status line, or modal. On a route switch, those already-open tabs must show an actionable response instead of silently submitting under another profile or executing a command with stale assumptions.

For the eight existing legacy POST paths (`ai-score`, `search`, `prompt`, `comment`, `vacancy-state`, `set-status`, `import-seen`, `add-manual`), the private runtime validates the exact old HMAC over the **old username**, looks up its explicit one-to-one target profile mapping, and requires the public same-origin `Origin`. If the JSON names a vacancy, the target profile must own it. A valid old shape returns HTTP `409` with `code: legacy_page_reload_required` and the Russian message “Страница обновилась. Перезагрузите её и повторите действие.” Reloading the original signed page URL mints the new cookie and loads the current interface. The response does not mint a cookie or execute the old command. An unknown or revoked mapping, bad signature, or foreign origin has no legacy migration grant; an explicitly unowned vacancy returns `404`. The old `import-seen` shape has no vacancy, so it only gets the reload instruction and cannot write into a fallback bucket.

This is **migration guidance, not legacy command parity**. The old synchronous `search` response, implicit vacancy fallback, unrevisioned writes and body-token authorization are not offered by the new API. The new page uses its cookie, explicit vacancy, revisions, idempotency key and asynchronous manual-run polling. Its `ai-score` and `add-manual` actions remain separate work. Existing open tabs must be reloaded before use after a route switch. No nginx route is switched by this change.
