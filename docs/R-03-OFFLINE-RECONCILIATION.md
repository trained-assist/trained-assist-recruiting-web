# R-03 operator-only offline reconciliation

`SqliteColdSearchReconciler` closes the synthetic crash window between a completed durable job and candidate-state materialization. It is **not** registered as a web route, MCP tool or background timer. Its authorization callback defaults to deny; an operator host must inject a trusted principal with the dedicated `recruiting.coldSearch.reconcile` scope and target-profile authorization. The caller supplies a unique operation ID, occurrence/job IDs, expected criteria/source/result revisions and an allowlisted reason code. No provider is imported or called.

The operation requires a blocked `outcome_unknown` occurrence. It finds the completed job only through the deterministic `schedule:<occurrenceId>` idempotency key, verifies profile, vacancy, criteria revision, source revision, request hash, result revision, completion timestamp and candidate vacancy IDs, then checks any existing snapshot against the same job. `BEGIN IMMEDIATE` uses one SQLite connection for candidate pool/seen/snapshot materialization, occurrence resolution, schedule unblock and a versioned audit receipt. A failure before commit rolls back all four. Repeating the same operation ID returns the original receipt; changing the command under that ID conflicts. A different operation ID for an already reconciled occurrence conflicts.

The receipt records the operator ID, target profile/vacancy, job/occurrence IDs, expected revisions, reason code, prior unknown error, original job completion time, reconciliation time and whether a snapshot was materialized. It contains no resume text, token or candidate details. The completed job's `completedAt` is the snapshot search time; reconciliation time does not make old candidates look newly searched.

The operator must first inspect the quarantined occurrence, completed job and expected revision values from the private SQLite fixture. A job still dispatching, partial, failed or `outcome_unknown` cannot be reconciled by this command. An unknown outcome without a completed matching job remains blocked for separate investigation. The test covers a completed job followed by a simulated crash, wrong principal/profile/vacancy/revisions, conflicting snapshot, rollback at receipt write, idempotent replay and no provider redispatch.

This is an offline domain operation, not a production operator CLI or permission system. Real authorization, audit sink, migration review, retention/backup, HH source verification and the non-GCP live cutover remain open under [HH #187](https://github.com/trained-assist/trained-assist-hh-skill/issues/187). Do not use synthetic fixture permissions as production identity.
