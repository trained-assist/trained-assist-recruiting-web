# R-03 legacy schedule import, offline and quarantined

The old `trained-assist-hh-skill/src/hh-cold-search-cron.js` emits five cron forms for `hh_proactive_search`: twice hourly (`m,m+30 * * * *`), hourly (`m * * * *`), stepped hours (`m phase-23/step * * *`), daily (`m h * * *`) and day step (`m h */days * *`). `legacyCronToPlan` accepts only those exact canonical forms and translates them to the schedule repository's Moscow-time plan. It rejects arbitrary cron expressions, malformed offsets, hours outside the legacy daily window, day steps above 31 and any unsupported syntax. An unsupported source definition must be reviewed rather than approximated. The original cron string is stored unchanged in both the schedule payload and a private import receipt.

`R03LegacyScheduleImport` consumes a versioned private definition envelope. It binds each source profile through an injected mapping, requires owned vacancies, the original `cold-search:<vacancy>` name, action and vacancy-only arguments, `Europe/Moscow`, and a paused source job. It maps each legacy job ID to one deterministic app schedule ID. All definitions are validated before one SQLite transaction writes them. The import is idempotent per legacy ID and migration ID; changed definitions conflict, and a mid-batch error rolls back all rows.

Every imported schedule remains `enabled=false` with a persistent `migrationQuarantine` and blocking marker. Even the three invented non-unknown outcomes require cutover review; the eight invented `unknown` outcomes are explicitly marked `legacy_outcome_unknown`. The worker cannot claim a due occurrence from these rows. The current synthetic command handler also rejects the invented imported vacancy IDs, and its migration guard blocks any imported fixture-compatible ID. No activation or replay command exists in this slice.

The invented golden from the preceding rehearsal supplies ten work and one test definition. Tests cover each legacy cron form, exact preservation, 11 unique rows, eight unknown outcomes, no due dispatch, idempotence, unsupported cron rejection and transaction rollback. This does **not** import real definitions, reconcile historical results, restore profile context or prove the target host's timer. An operator-reviewed activation design and the full HH #187 acceptance are needed before the GCP VM stop gate can clear.
