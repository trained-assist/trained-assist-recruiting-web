# R-01: first HH response read

This slice reads one live HH `response` negotiation page for an already trusted profile and an explicitly selected, owned vacancy. It preserves the HH negotiation and resume IDs as provider refs. The service loads the token from its server-side profile credential broker, sends `GET /negotiations/response?per_page=20&page=N&vacancy_id=...` with a host-configured `HH-User-Agent` name/contact header, refreshes once after 401, and projects a bounded response. Provider errors, malformed pages, a foreign vacancy and missing credentials return typed failures; no cached list is presented as current.

`GET /api/v1/ui/hh-responses?vacancyId=...&page=0` and `/hh/responses?vacancy_id=...` are mounted by the opt-in private web runtime only with Connected App BFF. The runtime wires the real profile credential broker and exact host-owned vacancy bindings. The default demo server and legacy signed-link private mode do not expose this page. Queryless `/auth/connected/start` is a static feature chooser with no grant, token or inferred profile. `/auth/connected/start?from=proactive` requests only `recruiting.candidateSearch`; `/auth/connected/start?from=responses` requests only `recruiting.responses.read`. This lets a responses-only member enter from the registered queryless app URL. The proactive and response pages link to each other by owned vacancy, and a browser session with the wrong read scope follows the corresponding explicit step-up. API and command routes retain scope denial. A missing response grant fails at callback and leaves the old candidate-search session intact, avoiding a redirect loop. The selected vacancy is an exact safe return path, never a supplied URL. The read-only page exposes HH fetch time and best-effort page navigation. No provider token reaches the browser.

This is an offline implementation and proposed route, not a live release. `infra/nginx/recruiting-responses.locations.conf` must be reviewed together with the existing Connected BFF auth-route snippet. Public nginx remains unchanged pending real CP membership and client registration, private HH provider canary, and route cutover review. No agent capability or MCP facade is declared for this UI read, so an MCP parity assertion is not applicable to this slice. If a response-read capability is later declared for agents, its real transport and handler need independent contract tests.

The page contract is [`v1-live-hh-response-page.schema.json`](../contracts/v1-live-hh-response-page.schema.json). `fetchedAt` means HH answered this request; `sourceRevision` hashes this page only. HH page-number pagination can shift when negotiations arrive or change state, so `paginationConsistency: best_effort` is explicit. It must not be treated as a complete, gap-free snapshot. A later R-01 slice needs pinned or reconciled multi-page reads, selected-vacancy persistence, resume/history context, UI and agent relay parity. Sending, moving, rejecting, draft generation and client reports remain separate commands and sources.

The tests use invented profiles, candidates, tokens and HH-shaped responses. They run the real private HTTP entrypoint, durable BFF, reader and credential broker with external CP/HH responses replaced; they cover two profiles, separate scopes, callback replay, CSRF gates, 401 refresh, provider failure, cross-vacancy rejection, page navigation and introspection outage. No real HH or user data is used.

## Exact response status (stacked follow-up)

The explicit “Текущий статус” link calls `GET /hh/response-detail?vacancy_id=...&negotiation_id=...`; the JSON equivalent is `/api/v1/ui/hh-response-detail?vacancyId=...&negotiationId=...`. After CP introspection and the `recruiting.responses.read` check, the private broker fetches only `GET /negotiations/{id}`. It checks the returned negotiation ID and vacancy against the trusted profile's host-owned vacancy binding, then returns a small current status projection. It does not call messages endpoints, infer actions, or alter a schedule. The default demo server and legacy signed-link mode do not mount it. Public routes in the nginx snippet remain proposals.

HH's [employer documentation](https://github.com/hhru/api/blob/master/docs/employer_negotiations.md#просмотр-списка-сообщений-в-отклике-приглашении) says fetching messages can mark an applicant response viewed. A message/history route therefore needs a separately reviewed effect permission and an explicit recruiter action; `recruiting.responses.read` is not sufficient authority to open messages. This status slice has fake-port HTTP tests only. Its exact-detail provider shape and returned status still need a private live HH canary before route activation.
