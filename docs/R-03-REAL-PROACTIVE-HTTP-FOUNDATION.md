# R-03 opt-in real proactive page and candidate API

`createRecruitingServer` can receive `realProactiveFeed` and `resolveRealVacancyOwnership` together. Only in this explicit mode do `GET /hh/proactive?vacancy_id=…` and `GET /api/hh/proactive/candidates?vacancy_id=…` read the real accumulated SQLite model. The same `resolveTrustedProfileContext` and `recruiting.candidateSearch` scope gate apply before either read. The ownership port must validate the exact profile/vacancy binding. The page escapes candidate fields and uses no script; the API and a future MCP adapter share `createRealProactiveRead`, which does not accept a model-supplied profile ID. The default server still serves the existing synthetic fixtures.

The integration factory `createR03AccumulatedRealFeedFromStores` binds the feed to `SqliteRealHhManualRuns.listAcceptedManualReceipts` and requires both to share one candidate-state instance. A manual snapshot is visible only after the durable run's verified completion receipt; a committed snapshot with `outcome_unknown` stays out. Scheduled results require a matching succeeded occurrence receipt. Tests exercise the same candidate projection through the transport-neutral read, HTTP API and escaped page, plus authentication, profile isolation, score overlay and an unknown manual run. Invented IDs and details are used throughout.

This is an offline opt-in foundation. With no `realProactiveActions` port, real mode returns `501` for unimplemented GET/POST paths in `/api/hh/proactive/*` rather than falling through to synthetic handlers; `/hh/proactive/app.js` is likewise unavailable because the real page is server-rendered. The action adapter described in `R-03-REAL-PROACTIVE-ACTIONS.md` implements a bounded subset. Other HTTP methods remain `405`. No production MCP transport advertises this read yet. The private data importer, canonical trusted profile and vacancy resolver, real HH/LLM evaluator, five-minute timer, indexed feed pagination, host deployment and cutoff acceptance under HH #187 remain open. The GCP VM routes are unchanged.
