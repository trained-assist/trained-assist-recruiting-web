# R-03 local MCP contract exercise

This slice pins two Recruiting-owned capability descriptions for schedule management and occurrence reads. The descriptor in `contracts/recruiting-capabilities-v1.json` names the handler operations, scopes, schema references and relay contract version. `contracts/capability-relay-v1.compatibility.json` records the relay-owned source revision and file digest used for the local compatibility check. The app does not own the production MCP↔HTTP relay or advertise these profile-scoped commands in its public C14 registry while trusted production identity is unresolved.

`npm run test:offline:mcp` starts a child process over stdio. Its test-only JSON-RPC fixture loads the descriptor and JSON Schemas, implements `initialize`, `tools/list` and `tools/call`, and sends calls to the real schedule handler created by `createRecruitingServer`. The test advances a fake clock and invokes the actual minute-tick handler through a private test hook. The provider is a stateful synthetic fixture; all network egress from that process is blocked. It checks profile/scope denial, unknown tool, protocol/relay version mismatch, schema-invalid arguments, one successful scheduled occurrence, completed result count, and quarantine without replay after an ambiguous provider result. The local client/fixture never starts Agent Run.

The tool list and input/output validators load the same descriptor and schemas checked into this repository. The relay compatibility file is a pinned copy of facts from the relay owner's contract; the test does not prove that a deployed runtime uses this pin. HTTP schedule routes and a trusted web session are still absent. The private `testing/*` methods exist only in the child process when `OFFLINE_MCP_TEST=1` and are not advertised as product tools.

This is a **local MCP contract exercise for R-03**, not full R-03 offline readiness: the page, manual search, schedule commands and occurrence reads have not yet been exercised together through an authenticated user entry point. It also does not establish integration or production readiness. Durable schedule/occurrence storage, real HH credentials and profile data, candidate stores/seen state/snapshots, background rescoring, public `/hh/proactive` and `/api/hh/proactive/*` parity, live provider behavior, and a verified non-GCP host are still required before the GCP VM stop gate in HH issue #187. Unknown legacy outcomes must be reconciled before any replay.
