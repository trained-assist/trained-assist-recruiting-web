# R-03 private legacy migration rehearsal, stage 1

The old HH service stores an accumulating `all-candidates.json` by resume ID, a per-vacancy `seen-ids.json`, dated `search-results-*.json`, query cache and comments, ATS context, and generic agent cron definitions. These do not map one-to-one to the current real-HH SQLite model. In particular, the real-HH model does not yet hold all legacy query/comment/ATS fields, and a legacy candidate with no `vacancy_ids` is a wildcard. This stage validates a **metadata projection** of those sources and commits only inventory counts and keyed HMAC fingerprints to a private SQLite database. It does not restore candidates, credentials, schedules or any legacy domain data.

`R03LegacyRehearsal` accepts a private envelope with per-profile candidate IDs and vacancy links, seen references, dated snapshot references, query-cache counts, comment references, ATS presence and paused schedule definitions. The private extractor must construct this envelope from a reviewed export; it must never copy raw candidate names, comments, queries, ATS text or tokens into the envelope or this repository. The validator rejects extra fields, missing profile bindings, foreign vacancies, dangling seen/snapshot/comment links, duplicate legacy job IDs, schedule definitions without ATS context, enabled schedules and count drift. A 32-byte operator-supplied HMAC key produces fingerprints without writing raw IDs or source profile refs to the staging DB. Keep that key outside Git and the DB. Errors expose stable codes, never input values.

`stage` writes the manifest and two profile summaries in one SQLite transaction. Repeating the same migration ID and fingerprint returns the existing summary; changed input conflicts. A failure during profile staging rolls all rows back. The invented golden has 11 paused schedules across work/test profiles, eight `unknown` outcomes, one wildcard candidate and one generated query cache. Those three classes are counted for quarantine. Unknown schedules are not replayed, wildcard records are not fanned out to vacancies, and generated query cache entries are not treated as current.

This is only a **preflight and metadata staging gate**. Next steps need a private source extractor, source-file checksums and backup, reviewed per-profile/vacancy mapping, a target model for comments/query/ATS and wildcard decisions, then a separate transactional domain restore with before/after counts and canary reads. Real PII and credentials must remain in restricted storage; no production state was read or changed in this PR. HH [#187](https://github.com/trained-assist/trained-assist-hh-skill/issues/187) remains the stop gate before the old GCP VM can be retired.
