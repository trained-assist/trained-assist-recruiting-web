# R-03 durable HH occurrence worker (offline)

`src/r03-durable-hh-worker.js` joins the existing SQLite schedule/occurrence repository to the injected HH search runner and real-HH candidate state. A due tick atomically claims a unique `(legacy_job_id, scheduled_at)` occurrence, derives one stable job ID, loads the trusted profile/vacancy plan and calls the shared scheduled search runner. Only a completed, profile-bound snapshot may mark the occurrence `succeeded`. `morningResults` reads candidates only through such a succeeded occurrence; a partial or uncertain run is never fresh. If a newer occurrence is incomplete, the previous result remains visible with `freshness: latest_run_incomplete`.

The worker uses an injected clock, plan loader, search port and state port. Tests use invented resume data and no network or credential. They cover persistence across process restart, overlapping claims, expired lease quarantine, provider failure, duplicate prevention, the morning read and a crash window after the candidate snapshot commits but before occurrence success. A failure at or after dispatch becomes `outcome_unknown` and blocks further schedule runs. Pre-dispatch missing plans can be rejected without pretending an HH request ran.

This is a domain integration slice, **not** an operational minute timer or live service wiring. The existing `r03-minute-worker.js` remains synthetic. The search runner and schedule repository use separate SQLite transactions; a committed candidate snapshot followed by a failed occurrence finish requires explicit operator reconciliation. The current synthetic reconciler does not yet support the real-HH snapshot schema, so such a run remains blocked in this slice. The worker does not import legacy IDs, implement trusted production profile/vacancy/credential loading, bind authenticated HTTP/MCP routes, perform ATS background scoring or call HH. The GCP VM stop gate in [HH #187](https://github.com/trained-assist/trained-assist-hh-skill/issues/187) remains open.
